## 我是怎么调接口的（已核对脚本，非脑补）

调用形如（Windows 的 bash / Git-Bash 里跑）：

```bash
node .agents/skills/gpt-image-assets/scripts/image-assets.mjs generate \
  --provider aipaiai \
  --quality 4K \
  --size 3840x2160 \
  --output assets/stickers/委屈掉泪_4k.png \
  --prompt "<英文为主的贴纸提示词，中文只出现在引号里，见下>"
```

脚本 `generate()`（image-assets.mjs:390-410）实际发出的 HTTP body：

```json
{
  "model": "gpt-image-2",
  "prompt": "<--prompt 原样透传，脚本不改写>",
  "size": "3840x2160",
  "quality": "4K",
  "response_format": "b64_json",
  "n": 1
}
```

POST 到 `https://aipaiai.cn/v1/images/generations`。关键事实：

- aipaiai `supportsOutputOptions:false` → **不发** `output_format`、**不发**
  `background`（image-assets.mjs:28、402-405）。
- `normalizeOptions`（201-232）对 prompt **零改动**，只对 size 做白名单校验、对 quality 做大写归一。
- aipaiai 尺寸白名单 =
  `1024x1024 / 1536x1024 / 1024x1536 / 3840x2160 / 2160x3840 / auto`（image-assets.mjs:25）。`3840x2160`
  在内，**校验通过、正常发出**（若不在白名单，脚本会先 `fail()`，根本不会请求）。
- 用户曾疑「4K 没进准许尺寸、退化成 1024」——**已证伪**：输出 JSON 记录 `size 3840x2160`、返回
  `width 3840 height 2160`、6.7MB、无 warning。用户看到的「1024 鬼图」是点错了旁边的老文件 `委屈掉泪.png`（与
  `委屈掉泪_4k.png` 仅差后缀）。

`545c 545c`，与源字符完全一致，未被转码破坏。故「模型收到的中文本身就是乱码」这条已否，见下嫌疑 0。

## 我排到的嫌疑（按优先级，供你判断）

0. **【已测试排除】命令行中文编码**：我原本最怀疑这条——Windows 的 bash 用 `--prompt "…呜呜…"`
   传参，若 argv 在 shell→Node 这段被 GBK/UTF-8 转码破坏，模型收到的就已是乱码。**已实测证伪**：`node -e "console.log([...process.argv[1]].map(c=>c.codePointAt(0).toString(16)))" 呜呜`
   得
   `545c 545c`，与源字符完全一致，`len:2`。argv 中文完好穿过 bash→Node，且脚本把 prompt 原样塞进 JSON（UTF-8 安全）。**模型收到的中文是正确的**，编码不是根因。
1. **【现最优先】模型端 CJK 渲染不稳**：模型收到正确中文，却在 1024² 和真 4K
   3840×2160 都把汉字渲成糊块/乱码。gpt-image-2 对密集汉字笔画本就抽奖式不稳定，与像素预算、画质无强相关。拉丁/数字笔画简单尚能凑，汉字直接崩。
2. **中转站对含 CJK 的 prompt 处理**：aipaiai 侧（或其背后真实模型）对多字节 prompt 的转发/编码是否有损——需抓一次真实请求/响应体确认发到上游的 prompt 仍是正确 UTF-8。

## 请你做的零成本诊断（不烧图）

编码已排除（见嫌疑 0），所以诊断重心在「发到上游的 prompt 是否仍正确」和「区分 CJK vs 通用文字能力」：

- **抓请求体确认上游收到的 prompt（分嫌疑 1/2）**：在 `generate()` POST 前临时
  `console.error(JSON.stringify(body))`，确认脚本手里 `body.prompt`
  的中文是正确 UTF-8（我这侧已验证 argv 完好，此步是把证据延伸到「即将发出的 HTTP
  body」）。若可能，再抓一次 aipaiai 的真实请求/响应，看转发到背后真实模型时 prompt 是否仍是正确 UTF-8——这能把嫌疑 2（中转站转发有损）钉死或排除。
- **英文对照（分离 CJK vs 通用文字）**：同结构 prompt 但引号内换纯英文（如
  `"woo woo"`）出一张。若**英文稳定清晰、中文崩**
  → 强指向嫌疑 1（模型端 CJK 渲染专门不行），而非通用文字能力或编码。这张会烧一次图，但结论价值高，建议做。
- **背后模型存疑**：`GET /v1/models` 只返回 `gpt-image-2`。确认 aipaiai 的 `gpt-image-2` 是否真是 OpenAI
  gpt-image 系（其 CJK 应尚可），还是套壳的其它模型（CJK 差）——这直接决定嫌疑 1 是否成立。

## 结论倾向与善后

- 编码已排除。若英文对照显示**英文稳、中文崩**，基本坐实**模型/中转站端 CJK 渲染不行**：回到「出无字图 + 后期叠字」，这是 100% 可控方案。
- 若抓包发现**发到上游的 prompt 已损**（嫌疑 2 成立）：那是中转站转发 bug，需换站或反馈站长；脚本侧可尝试从 UTF-8 文件读 prompt 再对照。
- 若英文也崩：那是通用文字渲染能力问题，与 CJK 无关，同样走叠字。

  RGB，没有 Alpha；肉眼看到的灰白网格是直接画进像素的假透明背景。三张新站失败图则是真 RGBA。这推翻了“Claude 不该在 prompt 中写透明背景”作为完整根因的判断。
- PNG 数据确认三张失败贴纸都是 RGBA：完全透明约 30%–35%，半透明约 18%–28%，完全不透明只占约 42%–50%。Codex 正常图均为 RGB，完全不透明。
- 角色恰好以白发、白衣、白尾为主，prompt 又大量使用
  `soft / pale / gentle`。模型生成的 Alpha 蒙版把主体和细线一并做成半透明，导致全图发白、发虚和细节丢失；文字只是最容易看出的症状。4K 只扩大画布，不能恢复被 Alpha 擦掉的细节。
- 用户进一步明确：旧 Zyuou 也生成过同类鬼图。因此 provider 切换、RGB/RGBA、透明 prompt、尺寸和中文文字都只能算观察变量，现有样本不能证明其中任何一项是根因。
- 两张旧站好图是 RGB 网格背景，三张当前新站坏图是 RGBA 且部分透明比例高；这是一项相关性，不是因果结论。当前没有“质量正常的同类 RGBA 贴纸”作为对照，也没有同 prompt、同 provider、同参数的重复样本。
- 目前应保留四类假设：模型或上游路由随机波动、浅色白色主体的 prompt 组合、部分输出的 Alpha 蒙版质量、同名模型背后的凭证分组或渠道映射差异。优先级可以调整，但不能再写成已确定根因。
- 真正区分这些假设需要受控测试：固定 prompt、provider、model、quality、size 和凭证分组，只改一个变量，并为随机性保留重复样本。未获得用户明确同意前不追加付费矩阵。
