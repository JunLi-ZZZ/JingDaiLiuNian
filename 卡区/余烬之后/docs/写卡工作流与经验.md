# 写卡工作流与经验

适用范围：带 MVU、EJS 和前端的开放文字角色扮演卡。来源：本卡实际反馈、镜待流年现有组织方式、AI创作指南六篇及创世回廊5.2相关实现。参考资料提供问题与做法，不自动成为本卡规则。

## 1. 先区分读者和执行者

每段内容先标注给谁看：作者维护文档、玩家界面、酒馆模型、数值脚本。模型看到的是最终提示词，通常不知道封面选项、按钮实现、历史修改理由。角色 description 也会进入提示词，不能当作商品简介。玩家已选定身份后，模型收到本局身份事实，而不是“可以选择默认或自定义”。

世界书说明世界事实、行动因果与输出要求；报错说明放在界面；修复策略写在代码与开发日志。用户提出一次问题，不等于应在提示词新增一条针对该事故的禁令。修改后逐句判断它是否对所有相关情境成立。

## 2. 分层后才定义字段

- 世界层：世界如何运行、人物如何获得信息与采取行动。
- 通用机制：品阶、技能获取、熟练、进化、战斗、旅行。
- 内容层：某项能力、人物、地区和物品的具体资料。
- 开局层：这局实际发生的前史、初始资源与第一幕条件。
- 当前状态：本局事实和近期变化。
- 接口层：模型怎样提交结构化更新，脚本怎样执行。

删掉当前开局再审查通用机制：若“旅行”失去了某项初始能力便无法理解，或者“首次建档”仍指名一个初始同伴，说明仍有耦合。换成另一种普通技能、另一位持有者再检查成长系统，不能把主角专属途径误当成人人通用机制。

## 3. 自由玩法不能被示例菜单替代

用户说进化开放时，正确入口是“进化”按钮调用 AI，依据当前能力、真实经历与处境生成方案；玩家可留空直接生成，也能补充意图重拟。把三种方向增加到七种仍然是固定菜单，不构成开放设计。

能力名称、作用、条件、代价与成长原理是内容。脚本的攻击、转化、技艺等结构是计算接口，不能把接口结构列成宇宙中仅有的能力种类。任意新增数值效果若没有实现执行器，应明确其当前可计算的部分与叙事判定部分，不把描述更新冒充已实现的数值机制。

## 4. 规则必须能指导下一次生成

独立规则写清定义、适用对象、触发、所需信息、过程、结果、持久化位置与关联机制。篇幅取决于机制复杂度；不能只放一句抽象口号，也不要重复 schema 全部字段和大量针对性案例。

首次/日常分别控制初始化与增量。已发生的行动进入结算，未选择的方案进入提案。当前身份用宏与本局档案明确映射。姓名、性别和来源从实际档案取值，逐层检查默认文案、角色关系、正文模板与生成提示词。

格式契约由 schema 派生，避免文字规则说一种类型、校验器要求另一种。数组元素是对象、可选参数默认值、空值含义必须一致。模型若把 JSON 对象编码成字符串，可做确定性解码；自然语言不能靠猜测转换成动作。

## 5. 先保证信息完整，再设计投影

完整档案和当前提示词是两份视图。状态投影按场景、近期名称与手动重点调入资料，旧见闻完整归档，稳定ID贯穿引用。摘要保留眼前生命资源、技能效果、任务、死亡原因、关系、时空与未完成事项；隐藏运行账本、实现规则ID和无意义空字段。

提示词长度以实际 EJS 执行后的文本检查；源码很长不代表注入很长，界面漂亮不代表模型收到的信息明了。字符数只能标作字符数，不能假称 token 数。游戏时间来自世界刻度和历法，不能随电脑时间变化。

## 6. 生成和落库是独立阶段

模型生成候选，脚本校验，界面展示实际变化，玩家确认后写入。取消、网络错误、消息页切换、版本变化均应有明确行为。失败变量保留原失败批次，只请求修复报错路径，其他有效更新合并后一次校验；不要重新生成全部变量放大错误范围。

本轮资源、时间、冷却、储能、死亡等在同一事务中执行。任何一个操作失败不留下半次更新。同一事件重放不二次扣费或增长熟练，状态与正文中的补丁应可追溯。

## 7. 前端按真实用途验收

正文能力获得、战斗、人物、旅行等记录各有布局。等级、品阶与来源分开呈现；共享品阶机制用于能力和物品，色彩与动画不替代文字信息。详情靠近点击项，加载提示完成后消失，空数据保留可理解入口。

按 1280、390、320 宽度检查真实组件，折叠、生成、取消、重拟、确认、切页都实际点击。浏览器模拟只能证明接口交互，不能证明在线模型生成质量。

## 8. 发布与新增卡隔离

每卡独立版本、构建目录、世界书绑定、打包和校验。原头像保留，旧产物保留。不调用另一张卡的升版脚本，不顺手改全局构建，不全量暂存脏工作区。检查最终 PNG 内 JSON、正则、脚本、世界书与头像图像块，而不只看源文件。

## 提交前逐项复核

1. 换一个开局后，通用规则仍成立吗？
2. 换成其他人物通过学习获得能力后，成长机制仍可用吗？
3. 当前自由生成是否又偷偷变成固定枚举或预填案例？
4. 模型看到的是事实，还是玩家界面和开发历史？
5. schema、规则、脚本、状态栏四处是否一致？
6. 报错修复是否只改变有问题的部分？
7. EJS 实际加载了什么、在哪个位置、是否重复？
8. 完整档案能否取回，当前投影是否漏掉关键因果？
9. 有哪些测试真正运行了，哪些仍需用户实机体验？
10. 日志是否写明本轮新发现的失误、根因和验收证据？


## 跨模型接回与玩法隔离（2026-09-22）

先存档实际文件，再对照回交说明。报告中的完成项、触发条件和标签名必须核对源文件；不能把说明当成实现。新增/删除世界书同时检查清单、生成器、EJS引用与打包结果。生成物改动回写源文件，字段改名提供旧存档迁移。

技术协议与故事文字分工：后续文字补充先写交接任务，作者审稿后由程序侧联调；明确动作执行器支持什么，参考卡的字段和机制不自动适用本卡。共享规则以任意持有者和任意能力来源检查；玩法的默认前史、赠予、死亡流程、专属ID与开场放独立目录。代码只搬文件不等于可自由切换玩法，还要说明初始化路由和仍未实现的入口。

验证分别记录源文本、解析结果、事务结算、楼层保存回执与卡片读取。含UpdateVariable不等于保存成功；辅助计算存在不等于AI生成当轮正文前已知确切结果。实机模型体验与离线模拟测试分开报告。

## 主角展示与名字解析（2026-09-22）

同一对象的身份和核心数值可在一张资料卡合并，正文协议与读取路径一起审查。品阶配色属性只接受品阶枚举，描述性标签沿用普通文字样式；检查实际计算样式，不能仅凭 DOM 存在就断定标题可见。

酒馆 persona 名在开局时通过助手宏接口解析，默认名字写入本局档案和主角实体。自定义姓名保留原值，并通过现有身份映射说明与 {{user}} 的关系。读旧存档时不自动改名。

文件备份和 Git 提交分别记录。Git 存档应包含提交号、确切路径和构建产物；工作区有其他卡的暂存项时使用限定路径的提交，保持原暂存项。

## 长期资料、全知建档与真实接口语义

世界书基础设定写稳定特征、历史成因、长期追求和条件性行为；本局位置、即时动作、关系进展与当前知识由变量记录。检查生成模板、传入参考、档案导出和预览示例四处，不能只改一段提示词。作者可以基于既有背景合理补全基础资料；人物获得信息需要其自身来源。留空策略不能普遍代替建档。

专属生成任务需要真实背景时，从绑定世界书和已登记资料取相关完整源条目，尊重关闭条目的按需使用；世界书控制器代码不能作为人物设定塞给模型。将请求内容与解析后的结果都纳入测试。

核对接口参数含义：getChatMessages的数字是楼层索引，负数是倒数深度。近期查询必须用真实深度并测试旧资料的召回，不能用永远返回相同数据的mock证明查询正确。

Git存档前核对被忽略的必需素材，指定本卡例外，使原头像和示例源能正常跟踪；检查从已提交文件构建的依赖，不以目录看起来干净代替完整性核验。


## 2026-09-23：EJS组合边界与文本重构交接

- 条目独立文件不等于JavaScript独立作用域。每条EJS自有的const/let放在局部块内，保留需要跨标签的块配对；测试多个控制器与变量列表实际合并后的代码、重复注入和外部同名变量。只改library名字会把故障推到state/actor/recent。
- 新增EJS要过tools/ejs-check.cjs打包闸门；变更生成模板必须改tools/generate.cjs，随后重生成和复测，不能只修生成后的变量列表。
- getChatMessages的正整数是固定楼号；近期几楼明确使用负索引逐楼读取，并用第2/3楼与最近楼内容不同的用例验证。
- 截图、离线复现、真实编译器、浏览器模拟、当前酒馆实机与在线模型是不同证据。开发日志写清实际到达哪一层；环境工具故障不掩盖成已看过后台。
- 大背景、神灵人设、神器个体、通用机制、专属能力、具体开局分层。默认体验只是选择后的实例；新增玩法不靠给通用提示词追加例外。初始选择、能力持有与开局场景应是可独立组合的数据。
- Claude文本与Codex程序接力前，保留可恢复存档，更新HANDOFF/CLAUDE最新入口；把确认事实、创作补充、待定决策和程序缺口分别交代。世界书的故事资料保持简洁，协作限制只进开发文档。
- 玩法自由度包含关系与日常。脚本负责需要计算的因果，世界书同时给情感交流、人物魅力、持续关系与精彩战斗提供正面创作指导。


## 2026-09-24：吸收Claude写作规范与序列迁移

写作前读取根目录《世界书写作规范.md》和10接回核验，按定义/列表/公式决定排版。同级键名表达同级概念；通用机制、个体能力、世界历史、角色长期档案、开局实例各有归属。正面表达事实、条件与结果；数值公式与执行器核对，修订经验进入开发日志。

规范的任务边界同样需要检查：主动技能不天然要求储能和冷却；世界书中的人物保留情感、动机与条件性行为。具体故事示例可能固化玩法，协议格式骨架则按接口需要清晰标识。已获用户认可的格式差异保留，单次反馈不变成全局批量替换规则。

术语改名分四层验收：新模型输出、旧存档读取、历史事件幂等比较、UI与EJS投影。保留字段名也仍需迁移旧枚举值。自然语言里的神话/传说不属于序列字段。特殊序列不擅自并入普通等级梯度。

新增世界书入包、EJS调用、数值执行器是三个独立完成条件。关闭源稿可随包保存，报告必须注明实际调用状态；不以文本存在代替玩法已实现。


## 2026-09-25：开放能力的接入边界

能力扩展应先定义稳定的通用档案，再把预设做成档案输入。程序只结算可组合且已定标的结构；完整描述、机理、条件、局限和情感/生活用途保留在能力档案，不能把所有能力压成固定枚举。`define` 用于新能力落档，`compose` 用于已经发生的素材转化；两者都走同一个事务与回执。

开局入口只负责组合人物档案、场景和初始能力选择。某个开局的死亡、奖励、伴生角色和专属世界书必须留在该开局模块，不能因为默认体验而写进通用能力规则。

预设不是限制：吞噬、合成、随机灵感等按钮提供低填写成本，生成后仍可编辑、重拟、保存和继续进化。验证必须覆盖“不选能力”和自定义能力，而不只检查默认选项。

通用执行器接入后补测事务失败：任一结果非法、资源不足、素材数量不足时，所有能力、物品、时间和账本保持原状。重放同一事件只返回既有结果。字段名相同不等于结构相同，精简操作契约应保留每种结构的真实内容。
